Abstract

A WebExtension can declare a service worker as its background context. Because WebExtensions have a permission model and user expectations that differ from those of web content, that service worker has access to capabilities that other service workers do not. This specification defines extension service workers, what distinguishes their realms for WebIDL, and the criteria under which a capability is made available to them.

Introduction

This section is non-normative.

A WebExtension can declare a service worker as its background context. Browsers make some capabilities available in that worker that are not available in other service workers. This is done where user permission is better granted at a different level in the extension permission model than the web offers, such as hardware access.

Today each such capability is implemented ad hoc, without specification, because WebIDL has no way to name "the service worker that belongs to an extension". The result is that the IDL of the owning specification does not match what Chromium, at present the only engine that ships these capabilities in extension service workers, implements:

API The IDL says Chromium ships The gap
WebUSB [WEBUSB] [Exposed=(Worker,Window)]: every worker, including every service worker. Added for extension service workers in whatwg/usb#221. Windows, dedicated workers, and the extension service worker. The IDL claims shared workers and all service workers. No engine implements that.
WebHID [WEBHID] [Exposed=(DedicatedWorker,ServiceWorker,Window)], with a note that a user agent "may" limit the service worker exposure to extension contexts. Added in whatwg/hid#97. Windows, dedicated workers, and the extension service worker. The restriction is in a note, not in the IDL.
Clipboard [CLIPBOARD-APIS] [Exposed=Window]. Service worker exposure for the web was declined in w3c/editing#458. The extension service worker, without user activation, gated on the extension’s clipboard permissions. No IDL describes the shipped exposure.

This specification does not define the lifetime of an extension service worker, and it does not revisit the processing model of service workers.

This specification defines extension service workers. To do so it:

  1. Defines the extension service worker realm, so that WebIDL can expose a construct in extension service workers without exposing it in other service workers.

  2. Sets the criteria this group applies before a capability is exposed to extension service workers. New behavior belongs in the feature’s own specification and in [SERVICE-WORKERS]. Exposure to extension service workers alone is for the cases where that has been considered and declined.

Conformance of user agents

The requirements in this specification are on user agents that implement [SERVICE-WORKERS] and support WebExtensions. They are stated in The extension service worker realm and Security considerations.

The criteria in Exposing a capability to extension service workers are applied by this group. They are not conformance requirements on any specification or user agent.

Extension service workers

A WebExtension can declare a service worker in its manifest under background.service_worker. The user agent registers it by running register the background service worker [webextensions]. The resulting service worker registration is the WebExtension’s background service worker registration. Its scope url is the WebExtension’s root URL.

The extension service worker of a WebExtension is the active worker of that WebExtension’s background service worker registration. A WebExtension has at most one active extension service worker at a time, and none if its manifest has no background.service_worker entry. The extension service worker is a privileged extension context. The origin of its script url is the extension origin.

Note: The definition is in terms of the registration rather than a particular service worker because the service worker is replaced when the extension updates, and the registration persists. Every service worker of the registration, including one that is still installing, has an extension service worker realm, because a worker’s realm is created before the worker becomes active.

The manifest is the only expected way to register an extension service worker. A document on the extension origin can nevertheless call register() with the extension root URL as the scope. Within an origin, [SERVICE-WORKERS] identifies a service worker registration by its scope url, so such a call names the background service worker registration and would replace its service worker with the script passed to the call.

This group needs to decide two things: whether such a registration is permitted at all, and, if it is, whether the resulting service worker is the extension service worker under the definition above.

An extension service worker is a secure context, as [SERVICE-WORKERS] requires, because [webextensions] makes each extension scheme a scheme the user agent considers to be authenticated in the sense of [SECURE-CONTEXTS].

The extension service worker realm

A realm is an extension service worker realm if it was created for a service worker of a background service worker registration.

Note: An extension service worker realm is defined by the registration the realm was created for, rather than by the realm’s eventual global object, because WebIDL decides exposure while the realm’s initial objects are being created, before [SERVICE-WORKERS] associates the global object with its service worker.

The extension service worker realm is meant to be used as a condition on the ServiceWorker entry of a construct’s exposure set in the [Exposed] extended attribute. The construct is then exposed in the extension service worker realm and not in other service workers. Entries for other global names are unaffected. A construct whose exposure set names Worker, which covers every worker global, lists DedicatedWorker and ServiceWorker separately so that the condition can be placed on the latter alone.

A user agent must not treat the presence of a construct in a realm as authorization to use the capability it provides. The extension’s permissions are checked on each use, independently of exposure, as described in Security considerations.

WebIDL does not currently allow a condition on an individual entry of an exposure set. Its exposure conditions ([SecureContext] and [CrossOriginIsolated]) apply to a whole construct. A proposal to WebIDL is being prepared. Until WebIDL accepts a mechanism, no specification can reference the extension service worker realm from IDL, and Current exposures describes intended exposure.

Exposing a capability to extension service workers

Criteria

When a capability is wanted in extension service workers, this group works through the following options in order and stops at the first that applies.

  1. Expose it to all service workers. The group asks the specification that owns the construct to add ServiceWorker (or Worker) to its exposure set. If the feature needs the worker to be started, kept alive, or notified, the owning specification uses the extension points of [SERVICE-WORKERS]: a functional event, an event handler on ServiceWorkerGlobalScope, and Fire Functional Event. If those extension points are insufficient, the missing hook is proposed to [SERVICE-WORKERS].

    The CSS namespace is not exposed in workers. An extension wants CSS.supports() for feature detection in its extension service worker (issue #1151). The feature needs neither a document nor a prompt, so exposure to all service workers applies: [CSSOM] exposes the namespace to all workers, as csswg-drafts#14229 proposes.

  2. Among service workers, expose it to extension service workers only. The condition is a public record from the group that owns the construct. The record either accepts an exposure intended for extension service workers or declines to expose the construct to all service workers for a reason the web cannot remove: the construct needs a chooser, a prompt, transient activation, or a permission that web content cannot hold without a document. In either case an extension permission takes the place of that gate.

    The owning specification limits the ServiceWorker entry of the construct’s exposure set to the extension service worker realm and calls the extension permission check where its algorithms would otherwise prompt or consult transient activation. Only the declaration that owns an interface can widen its exposure set.

    w3c/editing#458 asked the Web Editing Working Group to expose navigator.clipboard in service workers. The group asked for web use cases and noted that user activation is bound to a Window and that it would not pursue clipboard access without a focused document and a user-visible affordance. The request was not taken further for the web. These reasons are intrinsic to the web, so exposure to extension service workers only applies: an extension’s clipboardRead and clipboardWrite permissions take the place of the gate.

Neither exposure to all service workers nor exposure to extension service workers only is met by using Worker or ServiceWorker in an exposure set to mean "extension service workers" and narrowing the exposure in prose, in a note, or by leaving it to the user agent.

What the owning specification defines

A specification that exposes a construct to extension service workers defines the following.

The exposure.

The constructs whose ServiceWorker exposure is limited to the extension service worker realm, including every partial interface or member through which the construct is reached, such as a member added to WorkerNavigator. If the construct is also meant to be available in the extension’s windows or dedicated workers, those global names appear in the same declarations.

User-facing operations.

Any operation that presents a chooser, a prompt, or other user interface, or that requires transient activation, stays [Exposed=Window]. If such an operation is needed in a worker, what replaces the user interface and the activation.

Document assumptions.

For every algorithm step that consults transient activation, the relevant global object’s associated Document, a browsing context, or a top-level origin, what happens when the relevant global object is that of an extension service worker, which has none of these.

The permission.

Which manifest permission, host permission, or runtime-granted permission the extension permission check consults for the feature, in terms of the permission model of [webextensions].

Lifetime.

Whether, and how, pending work keeps the worker alive and whether any event starts it, using ExtendableEvent and functional events from [SERVICE-WORKERS], without assuming the worker stays alive longer than [SERVICE-WORKERS] allows.

Current exposures

For WebUSB and WebHID the owning specifications accepted exposure for extension service workers (whatwg/usb#221, whatwg/usb#224, whatwg/hid#97). For the Clipboard API the Web Editing Working Group confirmed that it does not wish to expose the API to all service workers (w3c/editing#458), and the exposure awaits the Web Editing Working Group attaching the condition.

Gecko and WebKit have no construct in this category. Gecko does not ship extension service workers by default. WebKit runs extension service workers and injects the browser namespace into them by script, but exposes no web platform interface in them beyond what the owning specification’s IDL says.

Security considerations

Exposing a construct in an extension service worker gives extension code headless access to a capability that the web gates on one or more of a document, a user gesture, and a prompt. The extension permission model of [webextensions] takes the place of those gates: the user consents when the permission is granted, at install time or at run time, and can withdraw it.

Where an algorithm of the owning specification would prompt, consult transient activation, or evaluate a document’s permissions policy, in an extension service worker it instead runs the extension permission check for the feature. A prompt is never shown from an extension service worker, and [PERMISSIONS-POLICY], which defines no policy for a service worker’s settings object, is not consulted.

The user agent must run the extension permission check on each use of the capability, so that a permission revoked while the worker is running takes effect on the next use.

The user agent must make use of such a capability from an extension service worker attributable to the extension in its user interface, since the tab-level indicators that accompany the capability in a window are not available.

Whether an extension service worker runs in a private browsing session, and with which granted permissions, is governed by [webextensions].

Privacy considerations

This specification exposes nothing to web content. An extension service worker realm belongs only to an extension service worker, whose script already runs with the extension’s permissions. What the headless path removes is the user gesture and the visible surface that accompany the same capability in a window, which is why Security considerations requires use to be attributable to the extension.

Conformance

Document conventions

Conformance requirements are expressed with a combination of descriptive assertions and RFC 2119 terminology. The key words “MUST”, “MUST NOT”, “REQUIRED”, “SHALL”, “SHALL NOT”, “SHOULD”, “SHOULD NOT”, “RECOMMENDED”, “MAY”, and “OPTIONAL” in the normative parts of this document are to be interpreted as described in RFC 2119. However, for readability, these words do not appear in all uppercase letters in this specification.

All of the text of this specification is normative except sections explicitly marked as non-normative, examples, and notes. [RFC2119]

Examples in this specification are introduced with the words “for example” or are set apart from the normative text with class="example", like this:

This is an example of an informative example.

Informative notes begin with the word “Note” and are set apart from the normative text with class="note", like this:

Note, this is an informative note.
